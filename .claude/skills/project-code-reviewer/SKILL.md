# 專案 Code Review

以 code review 角度檢查 TwoDo 專案的目前變更，優先找出會影響正確性、資料流、型別安全與後續維護的問題，再檢查風格與文件一致性。

## 工作原則

- 一律使用繁體中文回覆。
- 預設只審查本次相關變更；不要把使用者原本存在、且與本次任務無關的 dirty changes 混入結論。
- 先找阻擋合併的問題，再列建議改善；不要把偏好型建議包裝成必修項。
- 若沒有明確問題，要直接說明未發現阻擋項，並列出未驗證的殘餘風險。
- 不主動修改程式碼；此 skill 的輸出是審查結論與修正建議。
- 不要求新增測試；若缺少驗證會影響信心，只在殘餘風險中說明。

## 審查流程

1. 先確認變更範圍：
   - `git status --short`
   - `git diff --name-status`
   - `git diff --stat`
   - 必要時針對檔案讀取 `git diff -- path/to/file`
2. 判斷變更目的：
   - 依使用者需求、任務紀錄、spec、TSDoc、型別與實作推回改動意圖。
   - 若 diff 無法判斷意圖，明確列為待確認，不要猜測。
3. 依優先順序審查：
   - 風險與回歸：流程破壞、資料流錯誤、狀態不同步、例外路徑、非預期副作用。
   - 型別安全：interface 是否貼近資料結構、是否誤用 `as`、nullable/optional 是否清楚。
   - 維護性：命名是否表達責任、函式是否過長、條件是否難讀、責任邊界是否混雜。
   - 可延伸性：是否把可變規則硬編碼、是否讓後續新增欄位/狀態/流程變困難。
   - 專案風格：Vue、TypeScript、TailwindCSS、檔案命名、匯出方式與文件同步是否符合規範。
4. 只對可定位的問題給出檔案與行號；若是整體設計問題，指出主要相關檔案即可。

## TwoDo 專案檢查重點

- Vue 檔案：
  - 修改 `.vue` 前後要確認 `<spec lang="md">` 是否與行為一致。
  - 若有 `<script setup lang="ts">`，檢查型別與 TSDoc 是否同步。
  - 避免在 composable 中寫生命週期。
  - 優先使用 Composition API，不引入 Options API 風格。
- TypeScript：
  - 型別優先使用 `interface`；`type` 僅用於常數 union 或 interface 無法表達的情況。
  - 避免透過 `as` 強制指定型別。
  - 函式優先使用箭頭函式。
  - 優先使用具名匯出，避免預設匯出。
  - 型別與程式碼共置，並遵守 views/對應元件資料夾下的 `types/interface` 慣例。
- TailwindCSS 與樣式：
  - 除非遇到無法解決的複合樣式，優先使用 TailwindCSS 類別。
  - 第三方套件樣式非必要不要寫在全域樣式；需要覆寫時優先局部 scoped style。
  - 色碼必須參考 `src/assets/theme/color-variables.scss` 與 `src/assets/theme/theme-tokens`。
- 命名與結構：
  - 檔案、變數、函式、component 與 store 命名要能表達責任與資料語意。
  - 新增抽象需真的降低重複或隔離責任；避免只為了包裝而包裝。
  - 邏輯修改應讓主流程容易追蹤，避免把關鍵商業規則藏在 template 或過度巢狀條件中。
- 文件同步：
  - 行為、欄位名稱、函式簽章、回傳型別改動時，同步檢查 spec、TSDoc、介面註解與使用範例。
  - `<spec lang="md">` 內避免出現含尖括號的型別語法。

## 輸出格式

使用固定結構回覆：

```md
## 合併判斷
- 判斷：可合併 / 需修改 / 阻擋
- 理由：一句話說明核心原因。

## 主要問題
1. [阻擋/高/中/低] `檔案路徑:行號`
   - 問題：描述實際風險。
   - 原因：說明為什麼會影響正確性、維護性或專案規範。
   - 建議：給出可執行的修正方向。

## 維護性與延伸性
- 列出會影響理解、責任邊界或後續擴充的具體問題。

## 專案風格檢查
- 列出命名、檔案位置、TypeScript、Vue、TailwindCSS、spec/TSDoc 的符合或不符合項。

## 殘餘風險
- 列出尚未跑驗證、無法從 diff 確認或需要使用者決策的部分。
```

若沒有發現問題，仍保留相同結構，並在「主要問題」寫明「未發現阻擋或明顯維護性問題」。
